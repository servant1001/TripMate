# TripMate UI

建立平靜、實用的旅行規劃介面。除非使用者明確要求修改，否則保留既有資料結構、API 呼叫、事件處理器、Firebase Auth 流程、路由與權限。

## 正確開始

1. 編輯前先檢查頁面元件、相關樣式、專案使用的 UI 元件庫、既有共用元件與對應 state。
2. 重用 Vue 3、Element Plus、`@element-plus/icons-vue`、既有日期處理方式、dialog 與 message 模式。不要只為了少數 icon 或控制元件新增依賴。
3. 當 `App.vue` 或某個頁面元件包含多個彼此獨立的區塊時，將大型頁面區段拆成展示型元件。資料載入與商業邏輯 handler 留在父層，展示元件使用具型別的 props 與 emits。
4. 使用 scoped CSS 或元件前綴樣式。避免寬泛的 element selector 與無關重構。

## 設計 Token 與基準

除非當地已有 CSS 變數表達相同 token，否則使用以下預設：

- 深墨綠 `#123F3A`：主品牌色、強調標題、深色次要操作。
- 珊瑚色 `#FF735C`：主要 CTA 與作用中的重點點綴。
- 藍綠色 `#2F7D70`：連結、正向控制與輔助點綴。
- 頁面背景 `#F6F7F2`；卡片背景 `#FFFFFF`；邊框 `#E1E8E3`。
- 主要文字 `#163B37`；輔助文字 `#6B7D78`；淡綠底 `#EEF5F0`。
- 警示底色 `#FFF4D9`；破壞性顏色 `#D9544D`。
- 字體堆疊：`Inter, "Noto Sans TC", "PingFang TC", sans-serif`。
- 頁面內容寬度控制在 1180–1240px，桌機左右 gutter 32px，大卡片圓角 16px，輸入框/按鈕圓角 10px，陰影 `0 8px 24px rgba(18, 63, 58, 0.06)`。
- 頁面主標題使用 28–32px/700，卡片標題使用 18–20px/700，一般內容 14–16px，重要文字不可低於 12px。行高至少 1.5。

將 Element Plus 的 primary color 設為深墨綠，避免保留預設亮藍色操作。必要時在元件層使用珊瑚色 class 作為頁面主要 CTA。

## 共用互動與無障礙規則

- 使用可見 label、正確的 autocomplete 值、鍵盤 focus ring，以及清楚的 disabled / loading 狀態。
- 純 icon 控制項需要有無障礙 label 與 Tooltip。點擊區桌機至少 36px，觸控版至少 40–44px。
- 可修復的表單錯誤要顯示在對應欄位旁，不要使用 `alert()`。
- 保留破壞性操作前的確認步驟。保留既有成功後的 toast 訊息。
- 尊重 `prefers-reduced-motion`；hover 位移與 transition 控制在 150–200ms，modal 動畫不超過 250ms。
- 允許長標題與地點名稱安全地換行或截斷。375px 寬度下不可引入橫向捲動。

### 清單項目的更多操作

- 保持頁面層級可見的主要 `＋ 新增` 操作。項目層級次要操作——例如編輯、刪除、加入行程、上移/下移——應收進單一的 `更多操作` 選單。
- 使用既有的 Element Plus `el-dropdown` 搭配直接的 `el-button` trigger。不要用 `el-tooltip` 包住 trigger；請改用無障礙 label 與 `title`，因為額外 wrapper 可能讓 dropdown 無法接收到點擊。
- 保留既有 emits、刪除確認、權限檢查與成功/失敗訊息。破壞性 menu item 要明確標示並保留確認流程。
- 更多操作 trigger 在桌機至少 36×36px，在觸控版至少 40×40px。手機版請將唯一的 trigger 放在不會壓縮標題、金額或 metadata 的位置。

## Header 與頁面外殼

- 使用 64px 高的 sticky header，背景為半透明暖白色，底部有細邊框。
- 左側顯示 TripMate Logo。已登入使用者顯示頭像/縮寫與名稱，點擊後開啟帳號下拉選單；登出放在選單內。手機版必要時保留頭像、隱藏名稱。
- 產品 UI 中不要顯示 `Firebase 已連線` 或任何技術性連線狀態。
- 優先使用白色卡片與留白，而不是強烈分隔線或厚重陰影。

## 旅行詳情頁模式

### Hero 與導覽

- 在清楚的 hero header 中放置返回連結、國家/城市 chip、旅行標題、格式化日期區間、總天數與預算。
- 桌機右側放置 `成員管理`、`編輯旅行` 與緊湊的更多選單。手機版自然收合，同時保留 owner / editor / viewer 的限制。
- 針對 `行程`、`開銷`、`旅伴與結算` 使用導覽 links；使用深墨綠作用中文字與珊瑚色底線。窄螢幕允許橫向滑動頁籤。

### 主要版面

- 900px 以上使用 7:5 雙欄：左側行程、右側開銷摘要、下方全寬旅伴結算。欄距 20–24px，卡片頂部對齊。
- 900px 以下依序堆疊行程、開銷、旅伴/結算。600px 以下使用 16px gutter 與更緊湊的卡片內距。

### 每日行程

- 保留既有日期分組、拖曳排序、完成勾選、地圖連結、編輯/刪除與手機版上移/下移控制。
- 顯示 `ITINERARY`、`每日行程`，以及珊瑚色或深墨綠的 `＋ 新增行程` 按鈕。
- 每一天以 `DAY n` 與本地化日期呈現。使用時間軸：左側為完成 checkbox 與時間，中間為線與圓點，右側為可讀性良好的活動卡片。
- 卡片內優先呈現類型、標題、時長、地點與時間異常提示。地點前加入定位圖示，有連結時顯示外部地圖標記；否則使用弱化的 `尚未設定景點` 狀態。
- 編輯/刪除在桌機 hover / focus 時顯示，在手機版固定可用。保持完成勾選前後幾何穩定，降低完成項目強調但不要讓文字難以閱讀。
- `景點`、`餐廳`、`交通`、`住宿`、`商店` 的類型顏色系統要在主行程卡、個人行程卡與地點群組子卡片中一致重用。
- 群組卡 (`activityKind: group`) 需要與一般共同行程卡片有清楚視覺區隔，但不要為其內部子項目類型 chip 再額外建立一套顏色系統。
- 群組卡應支援使用者自訂顏色，並維持「預設色票 + 自訂選色器 + 即時預覽」的互動方式；若既有資料未設定 `groupColor`，必須自動回退到系統預設色。
- 當群組卡有自訂顏色時，應以 CSS 變數或同等方式同步控制卡片背景、邊框、標籤、摘要區與子卡片外框，避免只改一部分導致層級不一致。
- 當需要加入多選操作時，優先使用專屬的頂部選取操作列，例如 `全選目前顯示`、`取消全選`、`建立群組`、`刪除所選`，而不是在每張卡片內再加入更多按鈕。
- 明確區分 `解散群組` 與 `刪除群組`：解散群組會保留底下的子行程，刪除群組則會移除群組與其子行程。
- 可編輯時，空狀態要包含 icon、一句說明，以及 `新增第一個行程` 操作。

### 旅行開銷

- 顯示 `EXPENSES`、`旅行開銷` 與 `＋ 新增支出`，不要使用亮藍色主按鈕。
- 只從既有支出/成員資料推導：總支出、目前使用者已支付總額、目前使用者的應付/應收/已結清狀態。不要新增新的資料來源。
- 只有在真的有預算時才顯示預算進度條。沒有資料時不要加裝飾性圖表。
- 顯示分類 icon、標題、日期、付款人、分攤人數、金額，以及既有編輯/刪除控制。桌機版讓金額明顯且靠右，手機版安全堆疊。
- 使用明確空狀態，不要讓面板只剩大片留白。

### 支付與回饋

- 保持目前拆分成 `支付工具`、`回饋規則`、`付款明細` 的結構；不要把這些概念混成一張難以辨識的卡片。
- 回饋規則要依照清楚層級呈現：
  1. 基礎回饋摘要
  2. 加碼回饋摘要
  3. 上限與門檻資訊
  4. 已用額度拆解
  5. 條件標籤
- 在回饋規則 dialog 中，數字型上限欄位維持全寬，提示文字放在輸入框下方，而不是右側。
- 手機版支付畫面中的篩選器垂直堆疊，保留可見的生效中篩選 chip，當多個篩選或排序同時啟用時提供重設操作。
- 付款明細排序要明確且使用者可讀，例如 `最新優先`、`金額高到低`、`回饋高到低`。

### 購物清單與比價

- 購物卡片中的價格層級應依序呈現：原始商品金額、必要時的台幣換算、台灣售價、比價結果、價差或提示。
- `台灣售價` 與 `換算約 TWD` 都屬於輔助資訊；主要金額仍應優先顯示商品原始幣別金額。
- 比價 badge 應使用清楚但不過度刺眼的狀態樣式，例如：`當地較便宜`、`台灣較便宜`、`售價相同`。
- 若商品幣別不是 `TWD`，可顯示 `匯率日期` 與 `最新參考匯率估算` 的語氣，但不要把它包裝成實際刷卡或換匯成交價格。
- 與比價有關的第三方資料來源應透過既有 Worker endpoint 取得；不要在 UI 任意直連外部匯率服務。

### 旅伴與結算

- 摘要顯示旅伴數、總支付開銷與結算狀態。保留邀請碼可見性/管理權限。
- 邀請碼放在獨立卡片中並附複製按鈕；重用既有複製 handler 與成功 toast。
- 每位成員顯示頭像/縮寫、姓名、角色、已支付金額，以及清楚的綠色應收、珊瑚色應付或灰色已結清狀態 pill。
- 結算建議以 `付款人 → 收款人 金額` 卡片呈現，並保留既有有確認機制的 `標記為已結算` 操作。保留結算歷史與既有的還原確認流程。

## 表單、對話框與狀態

- 控制元件高度使用 46–48px，label 放在輸入框上方，圓角 10px，送出中需要阻止重複提交。
- 保留既有 Element Plus dialogs 與其 handlers；優化間距與響應式欄位，不要重寫驗證流程。
- 當表單需要從既有 TripMate 資料中選擇，例如收藏或行程項目時，優先使用可搜尋 / 可篩選的 picker dialog，而不是超長原始下拉選單。
- 只有在既有 state model 已經暴露出相關狀態時，才設計一致的空狀態、載入中、權限不足與失敗狀態。不要為了裝飾發明新的 API 或持久欄位。

## 登入頁模式

- 桌機版將內容置中於 `max-width: 1160px`、約 640px 高的 55/45 外殼中：左側是深墨綠旅行品牌區，右側是約 400px 寬的白色登入卡片。
- 品牌區顯示 TripMate Logo、`和旅伴一起，安排每一段旅程`、旅行規劃文案，以及三個精簡特色。插圖優先用 CSS 或專案既有資產，而不是新增依賴。
- 使用有 label 的 email / password 欄位、密碼顯示切換、鄰近的重設操作、珊瑚色送出按鈕、`或繼續使用` 分隔，以及有邊框的 Google 登入按鈕。保留所有既有登入、Google 登入、註冊與重設密碼功能。
- 驗證頁面不要顯示 app 層級的 header / 帳號 / 技術狀態控制。768px 以下隱藏插圖，改用緊湊 logo、20px gutter 與單張全寬卡片。

## 收尾與驗證

1. 若專案有設定 lint 指令就先執行，接著執行 `pnpm type-check` 與 `pnpm build`。若缺少 lint script，要明確回報，不要把它當成原始碼失敗。
2. 修正這次 UI 變更造成的回歸問題。不要忽略 TypeScript 錯誤。
3. 若是全站 UI 工作，使用 Playwright 擷取登入頁 1440×900 與 390×844，以及旅行詳情頁 1440×900、768×1024、390×844。若登入阻礙視覺測試，只能使用本地非正式資料 fixture；不要把 QA 資料寫入 Firebase。
4. 檢查字級、內容層級、無意義空白、CTA 色彩一致性、時間軸可讀性、金額強調、console error，以及所有要求尺寸下的橫向溢出。
5. 在交付說明中列出修改檔案、完成的 UI 與互動調整、驗證結果、部署狀態，以及任何延後處理項目。
